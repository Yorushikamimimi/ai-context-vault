# Session Commands

Use this when long conversations run out of context, move between tools, or need a quick status check. The owner says one short word; the agent does the whole routine. If unsure which one applies, treat it as a handoff. When a conversation's quota is about 70–80% used, call a handoff instead of waiting for it to run out; if the work cannot be finished, save the resume point first and leave commits to the next conversation.

## Shared step: write the resume point

Write it into the one current-progress document for this work (a project's current-progress file, or the matching task-memory note in the vault). Overwrite it in place; do not append a log. Six fixed fields, "none" when empty:

What is being done | How far it got | Next step | Decisions the owner made that are not yet in files | Uncommitted changes (yours vs. others') | What not to touch

## Commands

- **Brief** (answer only, no writes or commits): read the resume point and Git status first, then combine with the conversation; never from memory alone. At most ten plain lines: what is going on | what was finished and how far it moved (a rough percentage is fine) | what is not done | open problems and blockers | what waits for the owner's decision | recommended next step with its strongest objection. List every open item equally; the most recent topic gets one line, not more. Mark anything known from the conversation but missing from the resume point as "not yet in files".
- **Compress** (same conversation continues): write the resume point, no commit. Reply with one line naming the file and saying it is ready to compress, plus how many times this conversation has been compressed in this tool. Count only this conversation's own compressions; if unsure, say so. No fixed limit: start a new conversation when the tool's limits or forgetting call for it. The owner runs the compression.
- **Handoff** (new conversation, tool, or account): write the resume point and put every confirmed decision from the conversation into its file. In the vault, commit and push in batches per `close-out-and-commits.md`; in a project without commit authority, list the files waiting to be committed in the resume point. End with a copy-ready continuation prompt of at most ten lines: which file to read, where it stopped, the next step, what not to touch.
- **New conversation takes over**: read the files the continuation prompt names, restate goal, resume point, and next step in five lines, and wait for the owner to check. If correct, start; if not, the owner only points at files instead of re-explaining. Small gaps get filled when they come up; the standard is "the next step can be done right", not "nothing missed".
- **Close-out**: see `close-out-and-commits.md`; it includes writing the resume point. No continuation prompt unless asked.
- **Resume** (a responsibility exists in two tools; the owner worked in the other one for a while and closed out there): the owner says "resume" in the old conversation, no prompt needed. The old conversation treats its own memory as stale and lets files and Git win any conflict. It reads only this responsibility's resume point, commits made since it left (vault and project repositories), and shared rules changed meanwhile. Then five lines: where it stands now | what changed since I left | next step | what I remembered that has since changed | whether the other side left anything unclosed. Wait for the owner to check. If the responsibility's files have uncommitted changes, or the resume point is older than the other side's last commit, reply that the other side does not look fully closed out and ask what is missing. If the old conversation's memory is clearly broken (the restatement keeps missing even after pointing at files), switch to a handoff and a new conversation.
- **Health check** (coordinator only; writes and commits): answers "if this tool were unavailable, could any other agent take over from files alone?". Go through the responsibility index and the status page's list of active work: does each entry still exist, is its resume point no older than its repository's last commit, are uncommitted changes piling up? Look at status and dates only, not content, and do not enter private folders. Put decisions and states that live only in the conversation into the right vault files. Do not edit independent projects; mark them "progress behind, owner should say close-out in that conversation". Refresh the active-work list and the coordinator's resume point, then close out. Reply in at most ten lines: items checked, items fine, gaps found and what was filled, which conversation the owner should visit and what to say.
